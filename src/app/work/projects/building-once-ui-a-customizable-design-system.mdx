## Overview

As I build Gitstack — a tool designed to make managing code and workflows simpler, smarter, and more powerful — I’m documenting the journey step by step. One of the first hurdles I ran into was understanding how **CLI authentication** works. It always felt like black magic: I’d type `vercel login`, a browser would open, I’d click “Authorize,” and suddenly my terminal knew who I was. Now I finally understand what’s happening behind the scenes.

## How CLI Authentication Works

Most modern CLIs use a variation of the **device code flow**, part of the OAuth 2.0 standard. It’s a secure way to authenticate users without ever asking for their password in the terminal.

The process works like this:

1. You run a login command in the CLI.
2. The CLI opens a browser tab and directs you to the service’s website.
3. You sign in and grant access.
4. The service issues a secure **access token** on the backend.
5. The CLI, which has been polling for that token, retrieves it and stores it locally (usually in a config file).

From then on, every command you run includes that token when communicating with the service’s API. The API reads the token, verifies your identity, and determines what you’re allowed to do — all without exposing your credentials in the terminal.

## Real-World Examples

- **GitHub CLI (`gh auth login`)** uses browser-based OAuth to generate personal access tokens.
- **Vercel CLI (`vercel login`)** follows the same flow but links tokens to teams and workspaces.
- **Supabase CLI (`supabase login`)** uses a similar approach and relies on JWTs (JSON Web Tokens) internally.

## Why This Matters for Gitstack

Understanding this flow gives me a foundation to design Gitstack’s own authentication system. Instead of treating login as a black box, I now see it as a deliberate, elegant handshake between browser, server, and CLI. This is just the first piece of Gitstack’s puzzle — next, I’ll dive into how CLI commands actually talk to APIs.
